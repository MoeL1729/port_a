Docker 기반 통합 모니터링 & 로드밸런싱 홈랩

Windows PC 한 대 위에 컨테이너 8개로 3계층 인프라를 구축하고, 로드밸런싱된 웹 서비스를 무중단 운영하며 전체를 실시간 감시·자동 알림하는 소규모 운영 환경.

지원 공고의 우대사항(Zabbix/Grafana, HAproxy 프록시)을 "해본 적 있다"가 아니라 "구축·운영하고 장애까지 검증했다"로 만들기 위한 프로젝트.

[01] ARCHITECTURE

아키텍처 개요

외부 요청은 HAproxy가 받아 nginx 2대로 분산하고, 관제 계층(Zabbix)이 전체를 감시하며 장애 시 Telegram으로 통보한다. 모든 구성은 Docker Compose로 코드화(IaC)되어 있다.

[외부 PC / 스마트폰] │ LAN, :8082 ▼ ┌──────────────┐ │ HAproxy │ roundrobin + httpchk 헬스체크 └──────────────┘ │ │ ▼ ▼ [nginx web1] [nginx web2] ← 1대 다운 시 무중단 페일오버 ▲ │ (HTTP / 서비스 감시) ┌────────────────────────────────┐ │ Zabbix 7.0 + PostgreSQL │ 수집 · 판단 · 트리거 │ Grafana (시각화 대시보드) │ 관제 화면 │ Telegram (장애 자동 알림) │ 통보 └────────────────────────────────┘ 전체가 Docker host (Windows 11 + WSL2) 위에서 docker compose 로 선언·운영
[02] LIVE SCREENS

실제 구동 화면

직접 구축·운영 중인 홈랩의 실제 캡처. 컨테이너 8개가 모두 정상 기동 중이며, Grafana 대시보드에서 실시간 리소스를 관제하고 있다.

[03] BUILD SCOPE

구축 범위

단순 설치가 아니라, 운영 관점의 감시 체계와 고가용성 구조를 직접 설계·구성했다.

01컨테이너 기반 인프라 (Docker / IaC)

  • Docker Compose로 8개 컨테이너를 선언형(YAML)으로 정의, 명령 한 줄로 전체 스택 재현
  • named volume(데이터 영속성)과 bind mount(설정 주입·개발)를 용도에 맞게 구분 적용
  • 서비스 이름 기반 내부 DNS, depends_on 기동 순서, restart 자동복구 정책 활용
  • Dockerfile로 커스텀 이미지 빌드 — 개발용(bind mount)과 배포용(이미지 COPY) 방식 구분 이해

02통합 모니터링 (Zabbix + Grafana)

  • Zabbix Server 7.0 + PostgreSQL 백엔드, Agent2 기반 호스트 자원 수집
  • 3계층 감시 — 호스트(Linux 템플릿) / 서비스(HTTP Up·Down) / 컨테이너(docker.sock + LLD 자동발견)
  • 템플릿 없이 아이템·트리거 직접 정의 → 수집 파이프라인(아이템→트리거→액션) 구조 이해
  • Grafana 데이터소스 연동, 임계치 색상·Value Mapping 기반 관제 대시보드 구성

03장애 알림 자동화 (Telegram)

  • Zabbix Media type + Action으로 장애 발생 → 즉시 통보 → 복구 시 RESOLVED 통보 왕복 구현
  • 감지 → 발보 → 해소의 전체 알림 사이클 실측 검증

04로드밸런싱 · 고가용성 (HAproxy)

  • HAproxy로 nginx 2대 roundrobin 분산, option httpchk 헬스체크로 죽은 백엔드 자동 격리
  • 무중단 페일오버 검증 — 백엔드 1대 강제 종료에도 서비스 무중단 유지, 복구 시 자동 풀 복귀
  • stats 페이지로 백엔드 실시간 UP/DOWN 관제
[04] VERIFIED SCENARIOS

검증한 장애 시나리오

"구축했다"에서 멈추지 않고, 실제로 장애를 발생시켜 감지·대응·복구가 동작함을 직접 확인했다.

시나리오조치결과
웹 서비스 다운 docker stop web Zabbix 트리거 발동 → Telegram 알림 → 재기동 시 자동 해소
백엔드 서버 1대 장애 docker stop web1 HAproxy 헬스체크로 격리, 서비스 무중단 유지, web2만 응답
컨테이너 상태 변화 stop / start LLD 기반 컨테이너 감시로 상태 실시간 반영
[05] TROUBLESHOOTING LOG

직접 해결한 문제들

구축 과정에서 마주친 문제를 상류→하류로 원인을 좁혀가며 해결했다. 인프라 운영에서의 로그·세션 기반 장애 분석과 동일한 접근을 적용했다.

HW · BIOS 가상화(VT-x/SVM) 비활성
하드웨어 설정부터 WSL2·Docker까지 바닥부터 환경을 구성. 작업 관리자 가상화 상태 확인 → BIOS 진입 → CPU 가상화 활성화.
HAproxy 재시작 무한루프
로그에서 "Missing LF on last line" 확인, POSIX 개행 규칙에 따른 설정 파일 문제로 특정하여 해결. restart 정책이 설정 오류 앞에서 무한 재시작을 만든다는 점을 체감.
Zabbix Simple check 아이템 수집 실패
에러 메시지("must have IP parameter or host interface specified")를 근거로 키 파라미터에 대상 주소를 직접 지정하여 해결.
Grafana에서 호스트 미표시
호스트 그룹 소속 불일치가 원인임을 특정, 그룹 통일로 해결. "필터 문제와 데이터 문제의 구분"이라는 진단 원칙을 적용.
대시보드 상태 오표시
아이템별 값 정의(0/1의 의미)가 서로 다름을 확인, State running 아이템에만 UP/DOWN 매핑을 적용. 지표의 의미를 검증하지 않으면 대시보드가 잘못된 정보를 줄 수 있음을 학습.
[06] KEY TAKEAWAYS

배운 점

01

인프라는 코드다 (IaC)

절차가 아닌 선언으로 인프라를 관리하면 재현성과 변경 이력이 확보된다. 기존 방화벽 변경관리(요청–검토–적용–검증–기록)와 같은 원리를 코드로 수행하는 것.

02

감시는 계층으로 나뉜다

서버가 살아있어도 서비스는 죽을 수 있다. 호스트·서비스·컨테이너를 각각 다른 관점으로 감시해야 사각지대가 없어진다.

03

자동 복구는 만능이 아니다

restart 정책은 장애를 복구하지만 설정 오류 앞에서는 무한 재시작 루프를 만든다. 자동화에도 관찰이 필요하다.

04

대시보드는 거짓말할 수 있다

지표의 값 정의를 확인하지 않으면 살아있는 서버가 DOWN으로 표시되는 잘못된 관제 화면이 만들어진다.
